# Цепочка обмена

Сервис многостороннего обмена вещами. Пользователь публикует ненужную вещь и указывает,
что хотел бы получить взамен. Система строит граф совместимости и автоматически находит
замкнутые цепочки, в которых каждый участник отдаёт свою вещь и получает подходящую.

Такой подход снимает ограничение обычного обмена «один на один»: Алисе не обязательно
иметь именно то, что нужно Бобу. Например, Алиса отдаёт книгу Бобу, Боб передаёт настольную
игру Вере, а Вера отдаёт Алисе наушники — интересы всех трёх совпадают в одной цепочке.

**Развёрнутый стенд:** <http://170.168.16.116> — основной сценарий можно проверить без
локального запуска. Swagger там же: <http://170.168.16.116/swagger/>.

Пользовательский сценарий проходится с любого своего аккаунта после регистрации.
Админ-панель на стенде открывается демо-аккаунтом: логин `admin`, пароль `admin123`.
Локально администратора нет — флаг ставится вручную:
`UPDATE users SET is_admin = true WHERE nickname = '<ник>';`.

## Возможности MVP

- регистрация, вход по JWT в HttpOnly cookie, профиль и статистика пользователя;
- создание, просмотр, редактирование и снятие объявлений с автоматического поиска;
- несколько фотографий и выбор категорий вещей, желаемых взамен;
- фоновый поиск до 10 вариантов обмена длиной от 2 до 5 участников;
- ранжирование вариантов по рейтингу, надёжности и количеству участников;
- подтверждение, отказ, передача через ПВЗ и завершение обмена всеми участниками;
- защита одной вещи от участия в двух подтверждённых обменах;
- автоматическое восстановление поиска после отмены или срыва обмена;
- чат участников обмена, системные события и центр уведомлений;
- блокировка нежелательных пользователей и защита от повторных предложений;
- жалобы на сообщения и очередь модерации с просмотром контекста переписки;
- админ-панель со статистикой, управлением ПВЗ, доставками, обменами и пользователями;
- журнал действий администраторов;
- отдельный от сделок чат пользователя со службой поддержки.

| Авторизация | JWT, bcrypt, HttpOnly cookie | Аутентификация и защита пользовательских сессий |
| API-документация | Swagger / OpenAPI, swaggo | Интерактивное описание HTTP-контрактов |

| Интерфейс | SCSS Modules, React Hook Form, Lucide React | Формы, адаптивные стили и UI-компоненты |
| Инфраструктура | Docker, Docker Compose, Caddy | Одинаковый локальный и production-запуск, reverse proxy и TLS |
| Автоматизация | GitHub Actions, GHCR | CI, сборка образов и CD |

PostgreSQL выбран потому, что цепочка обмена — это связанные данные с жёсткими
инвариантами: одна вещь не может быть подтверждена в двух сделках, а состав цепочки
меняется только целиком. Транзакции, частичные `UNIQUE`-индексы, внешние ключи и advisory
lock держат эти правила на уровне БД, а не на уровне приложения. Разбор выбора и типов
данных — в [docs/db.md](docs/db.md).

## Архитектура и особенности реализации

### Поиск многостороннего обмена

Объявления являются вершинами графа, а желание владельца получить определённую категорию
задаёт направленное ребро. Рёбра вычисляются из актуальных `items` и `item_wants`, поэтому
после изменения объявления не нужно синхронизировать отдельную копию графа. DFS с
backtracking находит несколько замкнутых путей, не повторяя вещь или пользователя внутри
одного цикла. Подробнее: [как работает поиск обменов](docs/exchange-search.md).

Поиск выполняется фоновым worker после создания или значимого изменения объявления.
HTTP-запрос сразу возвращает сохранённую вещь, а ограниченная очередь последовательно
обрабатывает DFS-задачи, повторяет технические ошибки и не создаёт несколько одинаковых
задач для одной вещи.

### Целостность обменов

Найденный цикл сохраняется одной транзакцией. Канонические `signature` и
`composition_key`, частичные `UNIQUE`-индексы, блокировки строк и advisory lock защищают
от дублей и конкурентного подтверждения одной вещи в разных сделках. При подтверждении
одного варианта пересекающиеся предложения отменяются атомарно. Сорванный подтверждённый
состав не предлагается повторно, но замена хотя бы одной вещи снова делает цепочку
допустимой. Подробнее: [жизненный цикл обмена](docs/exchanges.md) и
[восстановление после отмены](docs/exchange-recovery.md).

### Модульный backend

Предметные области разделены на независимые модули. В каждом модуле HTTP handler отвечает
за транспорт, service — за правила предметной области, repository — за PostgreSQL, а DTO
и model отделяют внешний контракт от внутреннего представления. SQL хранится явно в
`queries/`, а `internal/db/` полностью генерируется sqlc.

Критичные переходы обмена, резервирование вещей, решения участников и административные
операции выполняются транзакционно. Ограничения и индексы в PostgreSQL остаются последней
линией защиты, даже если два запроса приходят одновременно.

### Frontend и связь с API

React-приложение использует TanStack React Query для серверного состояния и периодического
обновления чатов, уведомлений и статусов. Zod проверяет ответы API во время выполнения,
Redux Toolkit хранит состояние авторизации, а маршруты и тяжёлые страницы загружаются
лениво. В production Caddy раздаёт SPA и проксирует `/api/*` на Go API с одного origin.
Подробнее: [frontend/README.md](frontend/README.md).

### Безопасность и модерация

JWT хранится в HttpOnly cookie и не доступен JavaScript. Защищённые и административные
маршруты проверяются middleware на backend. Жалобы сохраняют автора, нарушителя,
конкретное сообщение и обмен; администратор видит контекст, принимает решение, может
заблокировать пользователя или отменить обмен. Решения модерации и ключевые операции
администраторов записываются в audit log. Подробнее: [авторизация](docs/auth.md), [жалобы](docs/reports.md) и
[журнал администраторов](docs/admin-audit.md).

## Запуск

```bash
cp .env.example .env
make up      # то же самое, что docker compose up -d
```

Поднимает БД, миграции, API и фронт. Образы пересобираются на каждый запуск
(`pull_policy: build` в compose), поэтому голый `docker compose up` тоже отдаёт
текущий код, а не тот, что лежал в local-теге с прошлого раза.

Приложение целиком — <http://localhost>. Swagger — <http://localhost/swagger/>,
см. `docs/swagger.md`.

Нужен только Docker с compose и buildx (`--mount=type=cache` в Dockerfile работает
через BuildKit; на Ubuntu это пакет `docker-buildx`). Если порт 80 занят, впиши в `.env`
свободный: `WEB_PORT=8081`.

Погасить — `make down`. Снести вместе с данными БД и подняться с нуля — `make reset`.

### Разработка

Гонять фронт и API вживую удобнее без пересборки образов:

```bash
make db      # только PostgreSQL с миграциями
make run     # API на порту из HTTP_ADDR (по умолчанию :8080)
make smoke   # проверка схемы на живой БД

cd frontend && npm ci && npm run dev   # Vite на :5173, /api уходит на :8080
```

Сервис `api` наружу не публикуется, поэтому `make up` и `make run` не спорят за `:8080`.

Здесь дополнительно нужны Go 1.26+ (goose и sqlc) и Node 22, как в CI и в образе веба
(нижняя граница vite 8 — 20.19, но проверяется сборка именно на 22).

## Тесты

Тестами закрыт слой, где ошибка стоит дороже всего: переходы статусов обмена, поиск
цепочек и права доступа.

- **Unit** — сервисы и модели: правила предметной области, проверки владельца и роли,
  ранжирование и очередь поиска.
- **Repository** — запросы против живой БД: транзакции, резервирование вещей, гонки при
  параллельном подтверждении. Без `DATABASE_URL` в окружении они молча скипаются.
- **Handler** — коды ответов и контракт ручек.
- **Integration** — сценарии целиком, за build-тегом `integration`, чтобы не удлинять
  обычный прогон: обмен от поиска до завершения, доставка, отказ участника,
  восстановление после срыва, тред, жалобы, блокировки и audit log.

```bash
go test ./... -race                 # unit, repository и handler
make test-exchange-integration      # сценарий обмена целиком
make test-delivery-integration      # сдача вещей в ПВЗ и доставка
```

Остальные integration-цели видны в `Makefile` по префиксу `test-`. Frontend
автотестами не покрыт — на нём работают типы TypeScript и ESLint.

## Линтеры

Backend — golangci-lint по `.golangci.yaml` в корне. Взят стандартный набор
(`errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`) и добавлены три линтера
под конкретные риски проекта:

- `errorlint` — ошибки всюду заворачиваются через `%w`, линтер ловит сравнение таких
  ошибок мимо `errors.Is`/`errors.As`;
- `bodyclose` — незакрытые `resp.Body` в HTTP-клиентах и тестах;
- `gosec` — JWT, bcrypt и сборка SQL-строк на auth-путях.

Проверка идёт и по integration-тестам (`build-tags: integration`), иначе они остались бы
вне контроля. Сгенерированный код исключён в режиме `lax`, а `G706` отключён точечно: там
аргумент — собственный argv CLI, а не пользовательский ввод. Обоснование каждого правила
лежит комментарием рядом с ним в конфиге. Запуск — `make lint`.

Frontend — ESLint по `frontend/eslint.config.js`: рекомендованные наборы `@eslint/js`,
`typescript-eslint`, `react-hooks` и `react-refresh`, поверх них — правила под ошибки,
которые дороже всего ловить в рантайме: `@typescript-eslint/no-explicit-any` (иначе
типизация API теряет смысл), `eqeqeq` и `curly` (неявные приведения и однострочные `if`),
`prefer-const`, `no-debugger` и `no-console` кроме `warn`/`error`. Неиспользуемые
переменные — ошибка, кроме префикса `_`. `npm run lint:ci` падает на любом warning,
поэтому предупреждения не копятся.

## CI

На каждый PR и push в `main`/`develop` работает `.github/workflows/ci.yml`:

- **lint** — golangci-lint v2.12.2 с пиннутой версией: новый релиз линтера иначе внезапно
  роняет зелёные PR. Стартует без БД и падает раньше тестов. `gofmt` и `go vet` отдельно
  не запускаются — их закрывает этот job.
- **backend** — поднимает `postgres:17-alpine`, катает миграции и гоняет
  `go test ./... -race` и integration-тест обмена. БД живая, поэтому тесты
  репозиториев не скипаются.
- **generated** — ставит sqlc v1.31.1 и swag v1.16.6, прогоняет `make sqlc` и
  `make swagger` и падает, если `internal/db/` или `docs/swagger/` разъехались с
  исходниками. Обновляешь версию генератора — правь и workflow.

Повторить локально (после `make up`; `DATABASE_URL` из `.env` должен быть в окружении,
иначе тесты с БД молча скипнутся):

```bash
make lint && go test ./... -race
make test-exchange-integration
make sqlc swagger && git status --short   # дерево должно остаться чистым
```

Фронтенд проверяет отдельный `.github/workflows/frontend.yml`: `npm ci`, `npm run lint:ci` и
`npm run build` на Node 22. Сборка там та же, что внутри образа веба, поэтому ошибка
TypeScript падает в CI, а не в `docker build`.

## Деплой

Push в `main` запускает `.github/workflows/cd.yml`: он собирает образы `api` и `web`,
пушит их в GHCR под тегом `github.sha`, копирует на сервер оба compose-файла и делает
`docker compose pull && up -d --no-build`. На сервере ничего не собирается, миграции
катает сервис `migrate` — тот же, что и локально.

Тесты в CD не дублируются: в `main` попадает только смёрженный PR, на котором прошёл CI.
Включи в настройках репозитория branch protection «require status checks», иначе прямой
push в `main` уедет на сервер непроверенным.

Секреты репозитория — три: `SSH_HOST`, `SSH_USER`, `SSH_KEY` (приватный ключ, публичный
лежит в `~/.ssh/authorized_keys` на сервере). `GITHUB_TOKEN` встроенный, заводить его не
нужно.

Сервер готовится один раз руками — нужен docker с compose и каталог `/opt/chain-of-trades`
с `.env` в нём. Compose-файлы туда положит сам деплой, а `.env` через GitHub не ходит:
`JWT_SECRET` и пароль базы живут там же, где том с данными. Отличия от локального `.env` —
`COOKIE_SECURE=true` и `SITE_ADDRESS=<домен>`, по которому Caddy сам выпустит сертификат.

Откат — прошлый образ ещё в GHCR, поэтому на сервере:

```bash
cd /opt/chain-of-trades
IMAGE_TAG=<sha предыдущего деплоя> docker compose \
  -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build
```

## Ограничения MVP

Осознанно не сделано — это хакатонный MVP, а не готовый к нагрузке продакшен:

- **Доставка эмулируется.** ПВЗ и статусы доставки живут в базе, интеграции с реальной
  логистикой нет: сдачу вещи отмечает пользователь, а завершение доставки — администратор.
- **Фотографии хранятся ссылками**, файлового хранилища и загрузки картинок нет.
- **Уведомления только внутри приложения** — ни почты, ни push.
- **Обновление данных опросом**, а не websocket: чаты, уведомления и статусы обмена
  подтягиваются периодическим refetch.
- **Поиск цепочек живёт одной фоновой очередью внутри процесса API** и ограничен длиной
  до 5 участников и 10 вариантами. На больших объёмах DFS придётся выносить в отдельный
  сервис.
- **Рейтинг и «надёжность» участника считаются по истории обменов внутри сервиса**,
  внешней верификации личности нет.
- **Бэкапов БД нет**: том `pgdata` — единственная копия данных.
- **Frontend без автотестов** — его закрывают только TypeScript и ESLint.

## Структура проекта

```text
.
├── cmd/                    # точки запуска API и мигратора
├── internal/               # backend-модули и бизнес-логика
├── migrations/             # версия схемы PostgreSQL
├── queries/                # исходные SQL-запросы для sqlc
├── db/                     # smoke-проверки схемы БД
├── frontend/               # React-приложение и Caddy
├── docs/                   # подробная техническая документация и OpenAPI
├── .github/                # CI/CD, шаблоны issue и pull request
├── Dockerfile              # сборка Go API и мигратора

└── docker-compose.prod.yml # production-оверлей с образами из GHCR
```
