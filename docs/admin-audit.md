# Блокировка пользователей и аудит администраторов

Этот модуль решает две связанные задачи: администратор может глобально закрыть
пользователю доступ к приложению, а команда видит, кто и когда совершил важное
административное действие.

## Глобальная и личная блокировки — разные вещи

`user_blocks` остаётся личным списком пользователя. Он нужен только для того,
чтобы нежелательный человек больше не участвовал с ним в подборе обменов.

Глобальная блокировка хранится в `users.is_blocked`. Она запрещает вход и любые
защищённые запросы. Middleware сверяет состояние аккаунта с БД после проверки JWT,
поэтому блокировка действует даже на cookie, полученную до блокировки.

## Ручки

- `POST /admin/users/{id}/block` — глобально заблокировать аккаунт;
- `POST /admin/users/{id}/unblock` — снять блокировку;
- `GET /admin/audit-log` — получить историю действий.

Журнал поддерживает `admin_id`, `action`, `from`, `to`, `limit` и `offset`.
Даты `from` и `to` передаются в RFC3339.

## Какие действия записываются

- назначение жалобы администратору;
- подтверждение или отклонение жалобы;
- просмотр переписки по жалобе;
- блокировка и разблокировка пользователя;
- принудительная отмена обмена.

В каждой записи есть UUID администратора, тип действия, тип и UUID объекта,
дополнительные данные в JSON и время.

## Атомарность

Блокировка аккаунта и запись аудита выполняются одним SQL-запросом. Назначение и
решение жалобы устроены так же. Принудительная отмена обмена пишет аудит внутри той
же транзакции, где меняется обмен. Поэтому состояние не может измениться без
соответствующей записи в истории.
