# Как система ищет обмены

Пользователь работает только с объявлениями и обменами. Граф, рёбра и DFS — внутренние
детали backend: frontend не должен знать о них и не должен запускать алгоритм отдельной
кнопкой.

## Коротко о процессе

Когда пользователь создаёт объявление, происходит следующее:

1. объявление и его желаемые категории сохраняются в PostgreSQL;
2. item service ставит идентификаторы объявления и владельца в очередь;
3. пользователь сразу получает созданное объявление, не ожидая DFS;
4. фоновый worker забирает задачу из очереди;
5. repository по запросу находит подходящие соседние объявления;
6. DFS собирает до 10 разных замкнутых обменов от 2 до 5 участников;
7. найденные варианты по очереди сохраняются отдельными транзакциями.

Отсутствие обмена — нормальная ситуация. Например, первому объявлению ещё может не хватать
двух других участников. Когда позже появится новое объявление, поиск запустится от него и
снова проверит доступные варианты.

## Как устроена асинхронность

Очередь находится в памяти процесса и вмещает 256 задач. Постановка неблокирующая: HTTP не
будет бесконечно ждать при перегрузке. Если очередь заполнена, объявление всё равно уже
сохранено, а ошибка постановки фиксируется в логе.

Для одного объявления одновременно существует не более одной обычной задачи — повторный
`PATCH` не размножает одинаковые поиски, пока предыдущий ожидает или выполняется. Recovery
после отмены является отдельной задачей: вместе с объявлениями он переносит
`composition_key`, который нельзя немедленно предлагать снова.

Один worker обрабатывает задачи последовательно. Это сознательно ограничивает нагрузку на
PostgreSQL: несколько DFS не начинают одновременно обходить один граф. На одну попытку
отводится 30 секунд; техническая ошибка повторяется до трёх раз. После окончательной ошибки
задача освобождается, worker пишет причину в лог и продолжает следующую.

При штатном завершении API сначала перестаёт принимать HTTP-запросы, затем закрывает вход
очереди и даёт worker дочитать буфер. Если за 35 секунд он не закончил, его context
отменяется принудительно.

Очередь пока не является постоянной: аварийное завершение процесса теряет ещё не начатые
задачи. Для MVP это приемлемо благодаря повторным триггерам поиска и актуальному чтению
графа из БД. Для гарантированной доставки следующим шагом нужна таблица jobs или внешний
broker, а не усложнение DFS.

## Что является вершиной и ребром

Вершина графа — объявление из таблицы `items`.

Для алгоритма достаточно двух идентификаторов:

- `item_id` — какое объявление рассматривается;
- `owner_id` — кому оно принадлежит.

Ребро `A → B` существует, если владелец объявления A хочет получить вещь категории B.

Пример:

- у Алисы книга, она хочет категорию `hobby`;
- у Боба настольная игра категории `hobby`;
- значит, существует направление `книга Алисы → игра Боба`.

Направление важно. Желание Алисы получить хобби-вещь ещё не означает, что Боб хочет книгу.
Для замкнутого обмена подходящее направление должно существовать на каждом его шаге.

## Почему нет отдельной таблицы рёбер

Рёбра не сохраняются в `compatibility_edges`. Они вычисляются запросом
`FindExchangeNeighbors` из актуальных данных `items` и `item_wants`.

Это решение выбрано для MVP по трём причинам:

- не нужна отдельная миграция и синхронизация таблицы рёбер;
- изменение категории или желаний сразу учитывается в следующем поиске;
- невозможно получить устаревшее ребро после изменения или удаления объявления.

Цена решения — PostgreSQL повторно вычисляет соседей во время DFS. Для MVP и максимальной
глубины 5 это проще и надёжнее постоянного кэша совместимости. Если объём данных станет
большим, рёбра можно будет материализовать отдельно, не меняя сам принцип DFS.

## Как repository находит соседей

Запрос начинает с текущего объявления, читает его строки из `item_wants` и выбирает
доступные объявления нужных категорий.

Дополнительно он исключает:

- само текущее объявление;
- другие объявления того же владельца;
- объявления, чей статус не позволяет участвовать в поиске;
- объявления, от которых владелец текущего уже отказался (`item_refusals`).

Результат сортируется по времени создания и UUID. Благодаря стабильной сортировке один и
тот же набор данных приводит к одинаковому порядку найденных вариантов.

SQL находится в `queries/exchange_search.sql`, а sqlc генерирует для него типобезопасный
Go-метод.

## Как работает DFS

DFS — поиск в глубину. Алгоритм берёт одного соседа, идёт по этому направлению дальше и
пытается вернуться в начальное объявление.

Для пути `A → B → C → A` работа выглядит так:

1. стартуем с A;
2. среди соседей A выбираем B;
3. среди соседей B выбираем C;
4. среди соседей C находим A;
5. путь замкнулся — обмен найден.

Если выбранная ветка зашла в тупик, DFS возвращается на шаг назад и пробует следующего
соседа. Это называется backtracking.

Алгоритм соблюдает ограничения:

- в обмене от 2 до 5 участников;
- одно объявление нельзя использовать дважды;
- один пользователь не может участвовать в одном обмене дважды;
- пользователи с блокировкой в любом направлении не попадают в один обмен;
- ребро, от которого владелец отказался, в графе отсутствует;
- шестой участник не добавляется;
- возвращение в стартовое объявление добавляет найденный цикл в результат;
- после найденного цикла DFS откатывает путь и продолжает обход других веток;
- один запуск возвращает не более 10 разных составов.

Во время обхода service хранит текущий путь и два набора посещённых значений: объявления и
владельцев. Поэтому повторения проверяются до углубления в следующую вершину.

Перед углублением DFS также проверяет нового владельца против всех пользователей текущего
пути через таблицу `user_blocks`. Если найдена блокировка в любом направлении, эта ветка
пропускается, а поиск продолжается со следующего соседа. Подробнее — в
[документации блокировок](user-blocks.md).

## Как найденный путь становится обменом

DFS возвращает последовательность объявлений. Service преобразует её в участников:

| Позиция | Пользователь | Отдаёт | Получает |
|---|---|---|---|
| 0 | владелец A | A | B |
| 1 | владелец B | B | C |
| 2 | владелец C | C | A |

Сам обмен записывается в `chains`, а участники — в `chain_participants`. Названия таблиц
остались историческими; во внешнем API и интерфейсе используется термин «обмен».

Сохранение выполняется одной транзакцией:

1. создаётся запись обмена;
2. добавляются все участники;
3. транзакция подтверждается только после успешной записи каждого участника.

Если запись хотя бы одного участника завершилась ошибкой, PostgreSQL откатывает всю
транзакцию. Полупустого обмена в базе не остаётся. Перед коммитом repository блокирует
строки всех вещей и повторно проверяет, что они всё ещё `available`. Поэтому устаревший
результат DFS не сохранится, если параллельно другую цепочку уже подтвердили и вещи стали
`reserved`.

### Как защищаемся от повторов

Для каждого обмена service строит каноническую подпись из направленных передач
`gives_item_id → receives_item_id`. Пары сортируются, поэтому обход одного цикла с другой
стартовой вершины даёт ту же подпись. Изменение хотя бы одного объявления или направления
передачи создаёт другую подпись.

Направленная подпись хранится в `chains.signature`. Дополнительно service строит
`composition_key` только из отсортированных `gives_item_id`. Поэтому разные направления и
перестановки одного набора вещей имеют разные `signature`, но одинаковый `composition_key`.

Оба ключа защищены частичными `UNIQUE`-индексами для активных статусов `proposed`,
`confirmed`, `delivering` и `delivered`. Два параллельных DFS могут одновременно не увидеть
результат друг друга при чтении, но PostgreSQL атомарно пропустит только один `INSERT`.
Конфликт считается нормальным результатом поиска: service исключает этот состав и пробует
следующую альтернативу.

Одно объявление может одновременно находиться в нескольких `proposed`-вариантах — это
нужно, чтобы пользователь выбирал не единственный случайно найденный цикл. Когда все
участники подтверждают один вариант, его вещи резервируются, а остальные активные
предложения с этими вещами атомарно переходят в `cancelled`. Одна вещь не может оказаться
сразу в двух подтверждённых обменах.

Закрытый обмен сам по себе подпись не держит. Раньше держал, и это молча запрещало
навсегда любую комбинацию, которую вытеснило чужое подтверждение (issue #55). Частичные
индексы поэтому формулируют общий инвариант как «не может быть двух **активных** обменов
с одним набором вещей».

Отдельное исключение — сорванный `confirmed`: его точный `composition_key` сохраняется в
`broken_exchange_compositions` и больше не принимается `CreateExchange`. Это не мешает
составу, где заменено хотя бы одно объявление, и не блокирует предложения, отменённые по
другим причинам. Создание обмена и запись запрета сериализуются одним advisory lock по
`composition_key`, поэтому параллельный DFS не проскочит между проверкой и коммитом.

## Чем помнится отказ

«Не предлагать то, от чего отказались» держится не подписью, а таблицей `item_refusals`:
отказ участника записывает пару «пользователь — вещь, которую он должен был получить», и
`FindExchangeNeighbors` вырезает это ребро из графа.

Подпись цикла была для этого неправильной единицей сразу в обе стороны. Слишком узкой: A
отказался от `A→B→C→A`, имея в виду «не хочу вещь B», а запоминалась конкретная тройка
людей — и `A→B→D→A` с той же вещью B предлагался снова. Слишком широкой: отказался C — и
состав умирал для A с B, которые оба были согласны.

Вырезанное ребро не зависит от того, с какого объявления начался обход, поэтому отказ
переживает смену остальных участников цикла, а рёбра, к которым отказ не относится,
остаются живыми.

Отказ помнится бессрочно: `created_at` заполняется, но в фильтре не участвует. Отсюда
известный перекос — если A отказался из-за третьего участника, а не из-за вещи B, вещь B он
больше не увидит. Лечится либо сроком давности (`AND refusal.created_at > now() - interval
'30 days'` — одна строка), либо причиной отказа в теле запроса, где «не хочу с этим
человеком» пишет в `user_blocks`. Второе честнее, но это расширение API.

Срыв уже подтверждённого обмена отказом от вещи не считается: там сорвалась передача, а
не разонравилась вещь. За виновника отвечает `deals_broken`, а от точного повторения всей
сорванной сделки защищает постоянный `broken_exchange_compositions`.

## Когда поиск запускается повторно

Задача поиска ставится автоматически:

- после `POST /items`;
- после `PATCH /items/{id}`, если изменились `category` или `wants`;
- после `PUT /items/{id}/search`, когда владелец возвращает снятое объявление;
- после `DELETE /items/{id}/search` — для остальных объявлений из автоматически
  отменённых предложений, но не для самой снятой вещи;
- после отмены обмена — и срыва подтверждённого, когда его объявления переходят из
  `reserved` обратно в `available`, и отказа от предложения.

Название, описание и фотографии не влияют на совместимость, поэтому их изменение не
запускает DFS.

Менять категорию или желания объявления в незавершённом обмене нельзя. Перед обновлением
repository проверяет участие объявления в таком обмене, а API возвращает `409 Conflict`.
Это не позволяет незаметно изменить уже предложенные участникам условия.

После отказа от ещё не подтверждённого `proposed`-обмена DFS тоже запускается, хотя граф
доступности не изменился: его объявления и до отказа оставались `available`. Это позволяет
сразу дополнить список альтернатив после исчезновения одного варианта. Переподставить
отказанное поиск при этом не может: отказ уже вырезал ребро.

## Что происходит при ошибках

Есть две разные ситуации:

1. **Обмен не найден.** Это успешный результат: объявление создано или обновлено, а обменов
   пока нет.
2. **Произошла техническая ошибка поиска.** Ошибка записывается в лог, но уже успешно
   сохранённое объявление не пропадает и пользователь не получает ложную ошибку создания.

При этом сохранение самого найденного обмена транзакционно, поэтому техническая ошибка не
может оставить частичный обмен.

## Ранжирование найденных обменов

DFS отвечает только за совместимость и собирает до 100 уникальных кандидатов. Затем exchange
service одним запросом получает статистику их участников, сортирует варианты и сохраняет не
больше 10 лучших. Благодаря расширенному пулу хороший вариант не теряется только потому, что
DFS обнаружил его одиннадцатым.

Итоговая оценка цикла складывается из четырёх нормализованных частей:

- 50% — средний рейтинг участников;
- 30% — надёжность по соотношению завершённых и сорванных сделок;
- 10% — подтверждённый опыт, ограниченный двадцатью сделками;
- 10% — компактность: при равных пользователях короткая цепочка выше длинной.

Для участника без оценок используется нейтральный рейтинг `3.0`. Надёжность считается со
сглаживанием, поэтому новый пользователь без истории не становится ни идеальным, ни плохим.

Рейтинг сглаживания не имеет — осознанно. Пока оценок не было ни у кого, вес 50% был
константой и на порядок не влиял вовсе; с первой оценкой он оживает как есть, и один отзыв
на единицу тянет цикл вниз сильнее, чем десять хороших поднимут. Если это окажется слишком
резким, лечится двумя строками в `cycleScore`: смешать балл с нейтральной тройкой по числу
оценок, как это уже делает надёжность. Откуда берутся сами оценки — [оценка партнёра](ratings.md).
Если итоговые оценки равны, применяется стабильная сортировка по каноническому составу вещей:
одинаковая база всегда выдаёт одинаковый порядок.

## Разделение по слоям

### Item service

Сохраняет и обновляет объявления, определяет, влияет ли изменение на совместимость, и
планирует поиск через небольшой интерфейс `ExchangeFinder`.

Item service не знает реализацию DFS и не работает с таблицами обменов напрямую.

### Exchange service

Содержит бизнес-логику: DFS, ограничение в 5 участников и 10 результатов, проверку
повторений, преобразование циклов в участников и сценарий `FindAndSaveAll`. Старый
`FindAndSave` оставлен как совместимая обёртка для одного результата.

### Search queue и worker

Queue дедуплицирует и буферизует задачи, worker управляет таймаутом и повторными попытками.
Они не знают SQL и вызывают `ProcessSearchJob` у exchange service.

### Exchange repository

Выполняет SQL-запрос соседей и транзакционное сохранение. Repository не решает, какой путь
является подходящим: это ответственность service.

### Handler

Возвращает сохранённые обмены через `GET /exchanges` и `GET /exchanges/{id}`. В handler нет
DFS и SQL.

## Основные файлы

| Файл | Назначение |
|---|---|
| `queries/exchange_search.sql` | вычисление соседей текущего объявления |
| `queries/exchange_save.sql` | запись обмена и его участников |
| `queries/exchange_read.sql` | чтение обменов для API |
| `internal/exchange/service/service.go` | DFS и полный сценарий поиска |
| `internal/exchange/search/queue.go` | bounded-очередь и дедупликация задач |
| `internal/exchange/search/worker.go` | фоновая обработка, retry и timeout |
| `internal/exchange/repository/repository.go` | PostgreSQL и транзакция сохранения |
| `internal/item/service/service.go` | автоматический запуск после Create/Update |
| `internal/exchange/handler/handler.go` | HTTP API найденных обменов |

## Проверка

Модульные тесты проверяют циклы из 2, 3 и 5 участников, несколько альтернатив, лимит в 10
результатов, ранжирование расширенного пула, нейтральную оценку новых пользователей,
дедупликацию перестановок одного состава, запрет шестого участника, backtracking, повтор
объявления, повтор владельца, отсутствие цикла и ошибки repository.

Интеграционные тесты создают пользователей и объявления в PostgreSQL, проверяют, что до
запуска worker обмена ещё нет, после обработки очереди он появляется, а выбор одного из
нескольких вариантов отменяет конкурирующий и резервирует только его вещи. Отдельный сценарий
подтверждает, что вариант с более надёжным участником сохраняется первым, даже если DFS нашёл
его позже.

```bash
go test ./...
make test-exchange-integration
```

Для интеграционного теста должна быть запущена локальная PostgreSQL с применёнными
миграциями.
