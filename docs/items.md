# Объявления: CRUD

Объявление — это вещь, которую владелец готов обменять, вместе со списком категорий,
которые он хочет получить взамен. Из этих желаний собирается граф обмена, поэтому
объявление без них бесполезно для подбора цепочек.

CRUD — четыре операции:

- **Create** — создать объявление;
- **Read** — получить объявление;
- **Update** — изменить объявление;
- **Delete** — удалить объявление.

В отличие от [пользователей](users.md), удаление здесь есть: вещь можно передумать менять.

## Маршруты

| Метод и путь | Что делает | Авторизация | Успешный ответ |
|---|---|---|---|
| `POST /items` | Создаёт объявление | нужна | `201 Created` |
| `GET /items/{id}` | Возвращает объявление по UUID | не нужна | `200 OK` |
| `PATCH /items/{id}` | Изменяет переданные поля | нужна, только своё | `200 OK` |
| `DELETE /items/{id}` | Удаляет объявление | нужна, только своё | `204 No Content` |
| `GET /categories` | Справочник категорий | не нужна | `200 OK` |

Защищённые маршруты читают cookie `access_token` — см. [документацию авторизации](auth.md).

## Категории

Категория указывается слагом, а не числовым id: слаг стабилен и не зависит от
переименования. Список берётся из справочника:

```http
GET /categories
```

```json
[
  {"slug": "bikes", "name": "Велосипеды и транспорт"},
  {"slug": "consoles", "name": "Игровые приставки"}
]
```

Неизвестный слаг — `400 Bad Request`, а не тихая подстановка чего-нибудь другого.

## Создание объявления

```http
POST /items
Content-Type: application/json
```

```json
{
  "category": "bikes",
  "title": "Велосипед",
  "description": "Почти новый, катался год",
  "photo_urls": [
    "https://example.com/bike-1.jpg",
    "https://example.com/bike-2.jpg"
  ],
  "wants": ["consoles", "phones"]
}
```

Обязательны `category`, `title`, `photo_urls` и `wants`; `description` можно не передавать.

Владелец берётся из cookie, а не из тела запроса: создать объявление от чужого имени
нельзя. Успешный ответ содержит созданное объявление и заголовок `Location: /items/{id}`.
Статус нового объявления — `available`.

## Получение объявления

```http
GET /items/8db9f3e2-8a45-4a70-b3d1-167b4f97e121
```

```json
{
  "id": "8db9f3e2-8a45-4a70-b3d1-167b4f97e121",
  "owner_id": "c80a1712-1cf2-4361-9711-39f212d404c7",
  "category": "bikes",
  "title": "Велосипед",
  "description": "Почти новый, катался год",
  "photo_urls": [
    "https://example.com/bike-1.jpg",
    "https://example.com/bike-2.jpg"
  ],
  "wants": ["consoles", "phones"],
  "status": "available",
  "created_at": "2026-08-05T01:47:11Z",
  "updated_at": "2026-08-05T01:47:11Z"
}
```

Карточка публичная: авторизация не нужна.

## Изменение объявления

`PATCH` меняет только переданные поля, остальные остаются прежними.

```http
PATCH /items/8db9f3e2-8a45-4a70-b3d1-167b4f97e121
Content-Type: application/json
```

```json
{
  "title": "Велосипед городской",
  "photo_urls": [
    "https://example.com/bike-1.jpg",
    "https://example.com/bike-2.jpg",
    "https://example.com/bike-3.jpg"
  ]
}
```

Менять можно `category`, `title`, `description`, `photo_urls` и `wants`. Нужно передать
хотя бы одно поле. Статус объявления этим маршрутом не меняется — им распоряжается механика
цепочек.

**Списки заменяются целиком.** `photo_urls` и `wants` — это не «добавить к тому, что есть»,
а «теперь ровно это». Отсюда все сценарии работы с фотографиями:

| Что нужно | Что передать |
|---|---|
| Добавить одну фотографию | старые ссылки + новую |
| Добавить несколько сразу | старые ссылки + новые |
| Удалить одну из трёх | две оставшиеся |
| Заменить все фотографии | только новые ссылки |
| Удалить все фотографии | невозможно: `[]` → `400` |

Пустой список и в `photo_urls`, и в `wants` — ошибка. Отсутствие поля в JSON и пустой
список различаются: первое означает «не трогай», второе — «сделай пустым», и второе
запрещено.

## Удаление объявления

```http
DELETE /items/8db9f3e2-8a45-4a70-b3d1-167b4f97e121
```

Успех — `204 No Content` без тела. Удалять можно только свои объявления.

Вещь, уже участвующую в цепочке обмена, удалить нельзя — `409 Conflict`. Иначе участник
цепочки остался бы без обещанного предмета. Запрет держит внешний ключ
`chain_participants → items ON DELETE RESTRICT`, то есть его нельзя обойти мимо API.
Желания удалённой вещи (`item_wants`) уходят каскадом.

## Проверка данных

- `title` после очистки — от 1 до 120 символов;
- `category` — слаг из справочника `GET /categories`;
- `photo_urls` — от 1 до 10 ссылок, каждая абсолютный `http`/`https`-адрес; относительные
  пути и другие схемы отвергаются, пустые строки отбрасываются;
- `wants` — от 1 до 10 слагов; регистр приводится к нижнему, дубликаты отбрасываются;
- ID в адресе должен быть корректным UUID;
- неизвестные поля в JSON не принимаются;
- тело запроса должно содержать ровно один JSON-объект и быть не больше 1 МБ.

Ограничение «хотя бы одна фотография» продублировано в БД
(`CHECK (cardinality(photo_urls) BETWEEN 1 AND 10)`), поэтому оно действует и для запросов
мимо API.

## Коды ответа

| Код | Когда возвращается |
|---|---|
| `200 OK` | Объявление получено или обновлено |
| `201 Created` | Объявление создано |
| `204 No Content` | Объявление удалено |
| `400 Bad Request` | Некорректный UUID или JSON, данные не прошли проверку, неизвестная категория, пустой список фото или желаний |
| `401 Unauthorized` | Нет или истекла cookie `access_token` |
| `403 Forbidden` | Объявление принадлежит другому пользователю |
| `404 Not Found` | Объявления с таким ID нет |
| `409 Conflict` | Вещь участвует в цепочке обмена |
| `500 Internal Server Error` | Непредвиденная ошибка на стороне backend |

Ошибки возвращаются в одном формате:

```json
{
  "error": "item not found"
}
```

`403` и `404` не смешиваются: владелец проверяется чтением объявления, а не условием в
`UPDATE`, иначе «чужая вещь» и «нет такой вещи» дали бы один и тот же ответ.

## Как запрос проходит через приложение

```text
HTTP-запрос
    ↓
handler — читает JSON, берёт владельца из cookie, формирует HTTP-ответ
    ↓
service — очищает данные, проверяет правила и права на объявление
    ↓
repository — выполняет запросы к PostgreSQL, вещь и желания пишет одной транзакцией
    ↓
sqlc — генерирует типобезопасный Go-код из queries/items.sql
```

Слои те же, что у пользователей, и делят работу так же (см. [users.md](users.md)).
Отличие одно: объявление живёт в двух таблицах (`items` и `item_wants`), поэтому создание и
изменение идут в транзакции. Без неё неизвестный слаг в `wants` оставил бы уже изменённые
поля объявления в БД при ответе `400`.

## Ограничения текущей версии

- Фотографии хранятся ссылками; загрузки файлов нет;
- списка объявлений с фильтрами и пагинацией пока нет, только карточка по ID;
- `status` через API не меняется — он появится вместе с механикой цепочек.

## Запуск и проверка

```bash
cp .env.example .env
make up       # поднять PostgreSQL и применить миграции
make run      # запустить API на localhost:8080
go test ./... # запустить тесты
```

Быстрая проверка (после `POST /auth/login` cookie лежит в `cookies.txt`):

```bash
curl -s -c cookies.txt -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Samir","password":"password123"}'

curl -i -b cookies.txt -X POST http://localhost:8080/items \
  -H 'Content-Type: application/json' \
  -d '{"category":"bikes","title":"Велосипед","photo_urls":["https://example.com/1.jpg"],"wants":["consoles"]}'
```
