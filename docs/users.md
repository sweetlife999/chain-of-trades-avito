# Пользователи: CRU без удаления

Этот модуль отвечает за базовую работу с пользователями: создать профиль, получить его
по ID и изменить данные. Удаления пока нет — для MVP оно не требуется.

CRU — это три операции:

- **Create** — создать пользователя;
- **Read** — получить пользователя;
- **Update** — обновить пользователя.

Буквы **D (Delete)** здесь нет, поэтому удалить пользователя через API нельзя.

## Маршруты

| Метод и путь | Что делает | Успешный ответ |
|---|---|---|
| `POST /users` | Создаёт пользователя | `201 Created` |
| `GET /users/{id}` | Возвращает пользователя по UUID | `200 OK` |
| `PATCH /users/{id}` | Изменяет переданные поля пользователя | `200 OK` |

`{id}` — UUID пользователя, например
`8db9f3e2-8a45-4a70-b3d1-167b4f97e121`.

### Создание пользователя

```http
POST /users
Content-Type: application/json
```

```json
{
  "nickname": "Samir",
  "password": "password123",
  "photo_url": "https://example.com/photo.jpg",
  "description": "Меняю настольные игры"
}
```

Обязательные поля — `nickname` и `password`. `photo_url` и `description` можно не
передавать.

Перед сохранением пробелы по краям текстовых полей убираются. Пароль не записывается в
БД открытым текстом: service превращает его в bcrypt-хеш, и только хеш передаётся в
repository.

Успешный ответ содержит созданного пользователя и заголовок
`Location: /users/{id}`. Ни пароль, ни его хеш в ответ не попадают.

### Получение пользователя

```http
GET /users/8db9f3e2-8a45-4a70-b3d1-167b4f97e121
```

Пример ответа:

```json
{
  "id": "8db9f3e2-8a45-4a70-b3d1-167b4f97e121",
  "nickname": "Samir",
  "photo_url": "https://example.com/photo.jpg",
  "description": "Меняю настольные игры",
  "deals_completed": 0,
  "deals_broken": 0,
  "rating": null,
  "created_at": "2026-08-04T13:00:00Z",
  "updated_at": "2026-08-04T13:00:00Z"
}
```

`rating: null` означает, что у пользователя пока нет оценок. Это не то же самое, что
нулевой рейтинг.

### Обновление пользователя

Используется `PATCH`, потому что клиент передаёт только те поля, которые хочет изменить.
Остальные данные сохраняются без изменений.

```http
PATCH /users/8db9f3e2-8a45-4a70-b3d1-167b4f97e121
Content-Type: application/json
```

```json
{
  "nickname": "NewSamir",
  "description": "Теперь меняю книги"
}
```

Можно изменить `nickname`, `photo_url` и `description`. Нужно передать хотя бы одно из
этих полей. Пароль этим маршрутом не меняется.

## Проверка данных

- nickname после очистки должен содержать от 3 до 32 символов;
- пароль должен занимать от 8 до 72 байт — верхняя граница связана с bcrypt;
- nickname уникален без учёта регистра: `Samir` и `samir` считаются одинаковыми;
- ID в адресе должен быть корректным UUID;
- неизвестные поля в JSON не принимаются;
- тело запроса должно содержать ровно один JSON-объект и быть не больше 1 МБ.

## Коды ответа

| Код | Когда возвращается |
|---|---|
| `200 OK` | Пользователь успешно получен или обновлён |
| `201 Created` | Пользователь успешно создан |
| `400 Bad Request` | Некорректный UUID, JSON или данные не прошли проверку |
| `404 Not Found` | Пользователь с таким ID не найден |
| `409 Conflict` | Такой nickname уже занят |
| `500 Internal Server Error` | Непредвиденная ошибка на стороне backend |

Ошибки возвращаются в одном формате:

```json
{
  "error": "user not found"
}
```

## Как запрос проходит через приложение

```text
HTTP-запрос
    ↓
handler — читает JSON и формирует HTTP-ответ
    ↓
service — очищает данные, проверяет правила и хеширует пароль
    ↓
repository — вызывает запросы к PostgreSQL
    ↓
sqlc — генерирует типобезопасный Go-код из queries/users.sql
```

Слои разделены намеренно:

- **handler** знает про HTTP, но не пишет SQL;
- **service** содержит бизнес-правила, но не зависит от HTTP;
- **repository** работает с БД, но не решает, какие данные допустимы;
- **dto** описывает JSON на входе и выходе;
- **model** содержит внутреннее представление пользователя.

Так каждый слой делает одну понятную работу, а логику можно тестировать отдельно.

## Ограничения текущей версии

- Авторизация ещё не подключена, поэтому `PATCH /users/{id}` пока технически не проверяет,
  что пользователь изменяет именно свой профиль. Это будет добавлено в issue #8.
- Сбросить `photo_url` обратно в SQL `NULL` пока нельзя. Фотографию можно заменить, а
  отдельная операция очистки появится при необходимости.
- Удаление пользователя для MVP не реализуется.

## Запуск и проверка

```bash
cp .env.example .env
make up       # поднять PostgreSQL и применить миграции
make run      # запустить API на localhost:8080
go test ./... # запустить тесты
```

Быстрая проверка создания пользователя:

```bash
curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Samir","password":"password123"}'
```
