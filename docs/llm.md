# Локальная модель

Рядом с API поднимается Ollama с маленькой языковой моделью. Сейчас это только
фундамент: сервис есть, деплой её довозит, клиент умеет спросить — но ни одной фичи
поверх модели ещё не написано.

Задач под неё две, и обе сводятся к одному и тому же действию — короткой
классификации с ответом по JSON-схеме:

- **антискам в чате обмена** — поймать увод сделки за пределы площадки («давайте
  спишемся в другом месте», «зачем ПВЗ, привезу сам»);
- **маршрутизация обращений в поддержку** — определить тему вопроса и ответить
  заранее написанным текстом.

Ни та, ни другая не генерирует свободный текст. Это не случайность, а следствие
железа — см. «Почему такая маленькая модель».

## Почему локальная, а не облачный API

Ключей и счёта не нужно, данные переписки не уходят наружу, а `docker compose up`
поднимает приложение целиком, включая модель. Цена — качество: то, что влезает на
этот сервер, умеет классифицировать и не умеет писать.

## Почему такая маленькая модель

Прод-сервер — **одно ядро 3 ГГц, 2 ГБ памяти, 25 ГБ диска, без GPU**. Память
распределяется примерно так:

| Что | Сколько |
|---|---|
| ОС | ~200 МБ |
| PostgreSQL | ~250 МБ |
| Go API | ~80 МБ |
| Caddy | ~40 МБ |
| сервер Ollama без весов | ~150 МБ |
| **остаётся на модель** | **~1.2 ГБ** |

Отсюда `qwen2.5:0.5b` — около 400 МБ в 4-битной квантизации, влезает с запасом. Тег
в Ollama уже instruct-tuned, отдельного файнтюна не требуется. Оценки прикидочные:
меряются на месте через `docker stats`.

Но ограничение по памяти — не главное. **Главное, что ядро одно.** Инференс на CPU
занимает его целиком, а второго ядра, чтобы обслуживать HTTP, пока считает модель,
на этой машине нет. Поэтому:

- любой вызов модели живёт в фоне, а не внутри HTTP-запроса;
- в прод-оверлее у сервиса стоит `cpus: "0.5"` — инференс становится вдвое медленнее
  и перестаёт душить API. Это единственное место в проекте с resource limits, и
  здесь они не страховка от масштаба, а условие работоспособности;
- генерация текста отпадает: 0.5B пишет по-русски плохо, а модель, которая пишет
  прилично, ни в память, ни в это ядро не помещается.

Отклонённые варианты:

- **7B или 3B** — не влезают в память, а на одном ядре дают меньше двух токенов в
  секунду;
- **две модели, по одной на задачу** — вдвое больше весов в памяти и перезагрузка при
  каждом переключении. Обе задачи — классификация, одной хватает;
- **облачный API** — см. выше;
- **файнтюн** — обе задачи решаются промптом.

## Клиент

`internal/llm` — два метода, только стандартная библиотека.

| Метод | Что делает |
|---|---|
| `Available(ctx)` | `GET /api/tags`: сервер поднят и нужная модель скачана |
| `Generate(ctx, system, user, format)` | `POST /api/chat`, один вопрос, один ответ |

`Available` намеренно **не запускает инференс**: греть веса ради проверки живости
значило бы занять единственное ядро в момент старта API. Отсутствие сервера и
отсутствие модели — разные ошибки (`ErrUnavailable` и `ErrModelMissing`), потому что
лечатся по-разному.

`Generate` шлёт `stream: false` (ответ короткий, склеивать куски незачем),
`temperature: 0` (классификации нужен воспроизводимый ответ) и ограничение на длину
ответа. Непустой `format` — это JSON-схема: Ollama принуждает ответ к ней сам,
поэтому разбирать прозу не нужно. Ответ возвращается строкой, а не `json.RawMessage`:
без схемы в нём лежит обычный текст, и выдавать его за JSON было бы враньём в типе.

Библиотеки под Ollama нет намеренно: это один GET и один POST на `net/http`, а
зависимость пришлось бы обновлять и объяснять.

## Как выключается

`OLLAMA_URL` пустой — и всё. Это единственная переменная в `internal/config`, пустое
значение которой не ошибка: `DATABASE_URL` и `JWT_SECRET` валят старт, а модель нет.
Она нужна отдельным фичам, а не самому API.

При запуске в лог уходит одна строка — модель готова, недоступна или выключена. На
старт это не влияет никак: сервис поднимается при любом исходе. «Недоступна» сразу
после деплоя — нормальный ответ, а не сбой: Ollama в это время ещё качает веса.

Отсюда правило для будущих фич: **сбой модели не должен ломать пользовательское
действие.** Сообщение в чат сохраняется независимо от того, посмотрел на него
классификатор или нет.

## Развёртывание

| Сервис | Что делает |
|---|---|
| `ollama` | Сервер модели. Порт только на `127.0.0.1`, наружу не смотрит |
| `ollama-pull` | Одноразовое скачивание весов и выход |

`ollama-pull` — тот же образ с другой командой, ровно как `migrate` рядом с `api`.
Том ему не нужен: качает сервер по `OLLAMA_HOST`, а не этот CLI.

Веса лежат в томе `ollama` и переживают деплой по тому же механизму, что `pgdata` и
`uploads`: `cd.yml` гасит стек через `docker compose down` **без `-v`**. Качать 400 МБ
на каждый деплой не приходится, а `make reset` сносит их вместе с базой.

**У `api` нет `depends_on` на Ollama.** Сайт обязан подниматься, пока модель качается.

Имя модели подставляется с дефолтом (`${OLLAMA_MODEL:-qwen2.5:0.5b}`), поэтому деплой
не требует правки `.env` на сервере — но переменной там можно переопределить.

## Ограничения текущей версии

- **Фич поверх модели нет.** `Generate` написан и покрыт тестами, но продакшн-вызывающих
  у него пока ноль — первым станет антискам-воркер.
- **Ответ не кешируется.** Одинаковый вопрос считается заново. До появления нагрузки
  измерять нечего.
- **Модель одна на весь сервис.** Понадобится вторая — понадобится и вторая машина.
- **Скачивание не проверяет целостность сверх того, что делает сам Ollama**, и при
  обрыве связи `ollama-pull` завершится ошибкой; лечится повторным `make llm`.
- **Веса выгружаются из памяти через 30 секунд простоя** (`OLLAMA_KEEP_ALIVE` в
  прод-оверлее) и возвращают память базе. Плата — перезагрузка с диска на следующем
  обращении; в фоновой задаче это незаметно.

## Запуск и проверка

```bash
make llm                                # поднять Ollama и скачать веса
docker compose logs ollama-pull         # чем кончилось скачивание
curl -s localhost:11434/api/tags        # модель в списке

go test ./internal/llm/...              # ни сети, ни Ollama: httptest
```

Поведение пинга на старте — три исхода:

```bash
make run                                     # llm: model ... is ready
OLLAMA_URL= make run                         # llm: OLLAMA_URL is empty ...
docker compose stop ollama && make run       # llm: model ... is not ready at startup
```

Во всех трёх случаях API поднимается и отвечает на `/health`.
