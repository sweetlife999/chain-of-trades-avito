# Локальная модель

Рядом с API поднимается Ollama с маленькой языковой моделью.

Задач под неё три. Две сводятся к короткой классификации, третья — к небольшому
структурированному тексту по JSON-схеме:

- **маршрутизация обращений в поддержку** — определить тему вопроса и ответить
  заранее написанным текстом. Сделано, см. «Автоответчик поддержки»;
- **антискам в чате обмена** — поймать увод сделки за пределы площадки («давайте
  спишемся в другом месте», «зачем ПВЗ, привезу сам»);
- **помощник объявления** — по рассказу пользователя предложить название, описание и
  одну категорию из актуального справочника БД.

Помощник генерирует только черновик, который пользователь видит до применения и может
исправить. Он не сохраняет объявление и не меняет заполненные поля без подтверждения.

## Почему локальная, а не облачный API

Ключей и счёта не нужно, данные переписки не уходят наружу, а `docker compose up`
поднимает приложение целиком, включая модель. Цена — качество: то, что влезает на
этот сервер, умеет классифицировать и не умеет писать.

## Почему такая маленькая модель

Прод-сервер — **одно ядро 3 ГГц, 2 ГБ памяти, 25 ГБ диска, без GPU**. Память
распределяется примерно так:

| Что | Сколько |
|---|---|
| ОС | ~200 МБ |
| PostgreSQL | ~250 МБ |
| Go API | ~80 МБ |
| Caddy | ~40 МБ |
| сервер Ollama без весов | 58 МиБ (замерено) |
| **остаётся на модель** | **~1.2 ГБ** |

Отсюда `qwen2.5:0.5b` — около 400 МБ в 4-битной квантизации, влезает с запасом. Тег
в Ollama уже instruct-tuned, отдельного файнтюна не требуется.

Замерено через `docker stats` по одной модели за раз:

| Состояние контейнера Ollama | RSS |
|---|---|
| веса выгружены | 58 МиБ |
| `qwen2.5:0.5b` (q4_K_M) загружена | 538 МиБ |
| `qwen2.5:0.5b-instruct-q8_0` загружена | 665 МиБ |
| обе загружены одновременно | 1.19 ГиБ |

Последняя строка — причина, по которой в прод-оверлее стоит `OLLAMA_MAX_LOADED_MODELS=1`:
две модели разом съедают весь бюджет.

Но ограничение по памяти — не главное. **Главное, что ядро одно.** Инференс на CPU
занимает его целиком, а второго ядра, чтобы обслуживать HTTP, пока считает модель,
на этой машине нет. Поэтому:

- любой вызов модели живёт в фоне, а не внутри HTTP-запроса;
- в прод-оверлее у сервиса стоит `cpus: "0.5"` — инференс становится вдвое медленнее
  и перестаёт душить API. Это единственное место в проекте с resource limits, и
  здесь они не страховка от масштаба, а условие работоспособности;
- длинная свободная генерация отпадает: 0.5B пишет по-русски нестабильно, а модель,
  которая пишет большие тексты прилично, ни в память, ни в это ядро не помещается.

Отклонённые варианты:

- **7B или 3B** — не влезают в память, а на одном ядре дают меньше двух токенов в
  секунду;
- **две модели, по одной на задачу** — вдвое больше весов в памяти и перезагрузка при
  каждом переключении. Обе задачи — классификация, одной хватает;
- **облачный API** — см. выше;
- **файнтюн** — обе задачи решаются промптом.

## Клиент

`internal/llm` — два метода, только стандартная библиотека.

| Метод | Что делает |
|---|---|
| `Available(ctx)` | `GET /api/tags`: сервер поднят и нужная модель скачана |
| `Generate(ctx, system, user, format)` | `POST /api/chat`, классификация до 32 токенов |
| `GenerateDetailed(ctx, system, user, format)` | тот же вызов, структурированный черновик до 256 токенов |

`Available` намеренно **не запускает инференс**: греть веса ради проверки живости
значило бы занять единственное ядро в момент старта API. Отсутствие сервера и
отсутствие модели — разные ошибки (`ErrUnavailable` и `ErrModelMissing`), потому что
лечатся по-разному.

`Generate` шлёт `stream: false` (ответ короткий, склеивать куски незачем) и JSON-схему в
`format`: Ollama принуждает ответ к ней сам, поэтому разбирать прозу не нужно. Ответ
возвращается строкой, а не `json.RawMessage`: без схемы в нём лежит обычный текст, и
выдавать его за JSON было бы враньём в типе.

Параметры инференса — константы пакета, а не аргументы вызова, и это не про удобство:

| Параметр | Значение | Почему |
|---|---|---|
| `temperature` | 0 | тот же текст даёт тот же ответ |
| `num_predict` | 32 / 256 | классификатору хватает 32, черновику объявления нужен небольшой запас |
| `num_ctx` | 1024 | вызывающий обрезает вход, больше не нужно |
| `num_thread` | 1 | в контейнере `nproc` показывает ядра хоста, а не квоту cgroup |

`num_thread` — главный из них. Без него Ollama поднимет столько потоков, сколько ядер у
машины, и будет молотить их внутри `cpus: "0.5"`. Значение — калибровочная ручка под
конкретный сервер, а не константа мироздания.

`num_ctx` и `num_thread` определяют раннер: если два вызывающих пришлют разные значения,
Ollama будет перезагружать веса на каждом переключении (замерено: +1–3 с к вызову).
Поэтому они и не аргументы.

**Время ответа определяется длиной запроса, а не длиной ответа.** Замерено на одном
потоке: 250 токенов промпта — 0.9 с, 690 токенов — 3.2 с, при том что сам ответ во всех
случаях 7–9 токенов. Отсюда обязанность вызывающего обрезать вход.

Воспроизводимость: при `temperature: 0` повторный запрос с тем же текстом даёт тот же
ответ, `seed` для этого не нужен. Но модель гиперчувствительна к формулировке — три
выброшенных из обращения слова могут сменить метку, — а число потоков меняет порядок
сложений в редукциях и тоже переставляет одиночные ответы (замерено: 11 из 15 при
потоках по умолчанию против 10 из 15 на одном потоке).

Библиотеки под Ollama нет намеренно: это один GET и один POST на `net/http`, а
зависимость пришлось бы обновлять и объяснять.

Все клиенты внутри процесса проходят через общий семафор инференса. Поэтому поддержка,
антискам и помощник объявления не запускают три вычисления одновременно на одном ядре.
Ожидающий запрос при этом уважает свой `context` и не зависает в очереди навсегда.

## Помощник объявления

`POST /items/ai-suggestions` принимает 10–1200 символов, создаёт задачу в памяти и
сразу отвечает `202`. Единственный воркер читает очередь, а фронт опрашивает
`GET /items/ai-suggestions/{id}`. Задачи принадлежат создавшему их пользователю и
удаляются через 30 минут; после перезапуска незавершённый черновик нужно запросить заново.

Категории модель не придумывает: перед каждым заданием сервис читает справочник БД.
Явные названия товара сначала проходят небольшой детерминированный словарь, а
неоднозначные — короткую LLM-классификацию, зажатую enum актуальных слагов. Такой
guardrail появился после живого замера: числовые индексы 0.5B перепутала в 5 случаях
из 5, а гибридная версия верно прошла тот же набор 5 из 5. Название и описание
дополнительно проверяются по длине и нормализуются; транслитный заголовок заменяется
первой русской фразой пользователя, а подозрительно разросшееся описание — исходными
фактами без генерации. Пользователь получает
превью с предупреждением и сам нажимает «Применить к объявлению» — только после этого
три поля формы меняются. Создание и редактирование объявления продолжают работать при
выключенной модели; помощник в таком случае отвечает `503`, не блокируя основную форму.

Пользовательский текст упаковывается в JSON как значение `item_text`, а промпт прямо
объявляет его данными, не инструкцией. Ответ зажат схемой из трёх полей, категория —
диапазоном существующих значений, поэтому prompt injection не может вызвать действие
на сервере или подставить произвольную категорию.

## Автоответчик поддержки

Новое обращение попадает в фоновую очередь, модель определяет его тему из пяти, и в тред
уходит **заранее написанный** текст под эту тему. Модель ничего не пишет и ничего не
знает про сервис: она выбирает одну из пяти корзин.

| Тема | О чём заготовка |
|---|---|
| `delivery` | пункты выдачи, передача вещи, статусы доставки |
| `exchange` | как собираются цепочки, статусы обмена, отказ |
| `payment` | комиссия, оплата, доплата между участниками |
| `account` | вход, пароль, никнейм, профиль |
| `complaint` | поведение другого участника, жалобы, блокировки |
| `other` | ответа нет — обращение сразу помечается «нужен человек» |

Тема `payment` появилась не из головы: вопрос «надо ли платить за обмен» модель уверенно
относила к `exchange` и получала в ответ рассказ про устройство цепочек, а вопрос про
комиссию попадал в `other`, у которого ответа по смыслу нет. Факт же у сервиса есть и он
простой — платежей в нём нет вообще. Это типовая причина заводить тему: **не «модель
ошиблась», а «корзины под этот вопрос не было»**.

**Почему тексты руками, а не генерацией.** Проверено: с фактами о сервисе в промпте на
пяти вопросах верным оказался один ответ. Модель выдумала функцию, которой нет
(«модератор восстановит пароль»), а на вопрос «можно отдать вещь лично?» ответила «Да,
конечно!» — при том что строкой выше в промпте было написано обратное. Выдуманный ответ
от поддержки хуже молчания, потому что пользователь по нему действует.

**Точность — 14 из 19** на замороженном наборе обращений (`bot_llm_test.go`), порог в
тесте 13. Ошибки чаще всего уходят в `exchange`: сервис про обмен, и модель тянет к самой
«центральной» теме. Поэтому каждая заготовка начинается с признания, что ответ
автоматический, и кончается тем, что обращение уже в очереди к человеку: цена промаха —
один абзац не по делу, а не неверное действие.

**Промпт трогать только с замером.** Он на английском при русских обращениях (так
точнее). Что даёт замер:

| Версия промпта | Результат |
|---|---|
| текущая: шесть тем, шесть примеров | **14 из 19** |
| пять тем без `payment`, пять примеров | 11 из 19 |
| шесть тем, но пять примеров | 12 из 19 |
| пять тем, восемь примеров | 10 из 16 |
| пять тем, пять примеров | 11 из 16 |
| с правилом «не уверен — отвечай other» | 6 из 15 |
| номера ответов вместо слов-меток | 5 из 15 |

Из таблицы следуют три правила, и ни одно не было очевидным заранее:

1. **Ровно один пример на тему.** Не «чем меньше, тем лучше»: восемь примеров на пять тем
   хуже пяти, а шесть на шесть — лучше пяти. Появится седьмая тема, понадобится и седьмой
   пример.
2. **Никаких дополнительных инструкций.** Правило дефолта уронило результат вдвое: место
   в промпте у 0.5B кончается быстро, а отрицаний вида «never guess X» она не держит.
3. **Связь между правкой и результатом не прямая.** Правка ради обращений про статус
   доставки как раз их и не вылечила, зато починила два посторонних кейса. Поэтому
   `make test-support-bot-llm` — не формальность, а единственный способ узнать, стало
   лучше или хуже.

Одна и та же версия промпта в ручном пробнике однажды разошлась с клиентом на один кейс:
на результат влияет и состояние раннера, не только текст запроса. Отсюда порог на единицу
ниже замера.

Одна и та же версия промпта в ручном пробнике дала 12 из 16, а через клиент стабильно
даёт 11: на результат влияет и состояние раннера, не только текст запроса. Отсюда порог
на единицу ниже замера.

**Prompt injection закрыт устройством фичи.** Выход зажат enum из пяти значений, текст
написан руками, поэтому «игнорируй инструкции» максимум выберет не ту заготовку.

**Эскалация: когда обращение помечается «нужен человек».** Отметка `escalated_at` на
`support_threads` (миграция 00025) ставится в двух случаях, и оба означают одно — автоответ
вопрос не решил:

1. **пользователь написал в обращение повторно.** Первое сообщение вставляет
   `CreateSupportThread`, поэтому любой вызов `CreateUserSupportMessage` — это по
   определению второе сообщение или дальше, и отдельного счётчика не нужно;
2. **бот не справился с первого сообщения** — модель отнесла обращение к теме `other`
   либо не ответила вовсе (недоступна, таймаут, мусор вместо JSON). Ждать, пока
   пользователь напишет второй раз в пустоту, здесь незачем.

Отметка идемпотентна: повторные сообщения её не двигают, потому что это «когда стало нужно
вмешаться», а не «когда писали в последний раз». Это не статус: `in_progress` означает
«взято конкретным администратором», и эскалированное обращение остаётся эскалированным
после того, как его взяли.

**Очередь модерации по умолчанию показывает только то, что ждёт человека** —
`GET /admin/support/threads?needs_human=true`, и в админке этот режим включён сразу.
Условие фильтра состоит из двух частей, и вторая важнее первой:

- обращение эскалировано, **или**
- на обращение со стороны сервиса вообще никто не ответил.

Без второй половины из очереди пропадали бы обращения, пришедшие в момент, когда
автоответчик был выключен, недоступен или ещё не существовал: поломка модели прятала бы
обращения вместо того, чтобы их показывать. С ней свойство держится само собой — **бот
может убрать обращение из очереди, только если он на него действительно ответил.**

Само API по умолчанию отдаёт очередь целиком: сужает её тот, кто явно попросил
`needs_human=true`. Прятать обращения от клиента, который про параметр не знает, — не
поведение по умолчанию для очереди поддержки. Пометка «нужен человек» в строке очереди и
«автоответ не помог» в карточке обращения остаются: под снятым фильтром видно, какие из
показанных обращений ждут вмешательства.

**Что бот не делает:** не берёт обращение на себя (оно остаётся в очереди `open`), не
гасит непрочитанное у модераторов, не двигает `updated_at`, не отвечает второй раз в том
же треде и молчит, если обращение успели взять в работу. Все пять правил — условия в
одном SQL-запросе `CreateBotSupportMessage`, а не проверки в Go.

Автор ответа — служебный пользователь «Уми» (заведён миграцией 00024 под ником «У-бот»,
переименован в 00028 вслед за маскотом): бот говорит от его лица. Ник в базе и константа
`BotNickname` в коде обязаны совпадать, потому что вставка ответа находит автора джойном
по нику. Разъехавшись, они не дают ошибки: вставка возвращает ноль строк, и бот молчит на
каждом обращении. Поэтому совпадение сверяется на старте — в лог уходит
`support bot is disabled: user "Уми" is missing`, и это единственная строка, по которой
такую поломку видно.

Он `is_admin`,
потому что триггер `notify_support_message` по этому флагу выбирает получателя
уведомления; иначе ответ бота уведомил бы администраторов вместо автора обращения. Плата
— по одному мусорному уведомлению на бота с каждого сообщения пользователя: их никто не
читает, войти этим пользователем нельзя (пароль заведомо не bcrypt-хеш).

Ник виден пользователю над сообщением, и первая строка ответа честная намеренно: «я могу
ошибаться, позову модератора» не оставляет сомнений, что отвечает машина.

## Как выключается

`OLLAMA_URL` пустой — и всё. Это единственная переменная в `internal/config`, пустое
значение которой не ошибка: `DATABASE_URL` и `JWT_SECRET` валят старт, а модель нет.
Она нужна отдельным фичам, а не самому API.

При запуске в лог уходит одна строка — модель готова, недоступна или выключена. На
старт это не влияет никак: сервис поднимается при любом исходе. «Недоступна» сразу
после деплоя — нормальный ответ, а не сбой: Ollama в это время ещё качает веса.

Отсюда правило для будущих фич: **сбой модели не должен ломать пользовательское
действие.** Сообщение в чат сохраняется независимо от того, посмотрел на него
классификатор или нет.

## Развёртывание

| Сервис | Что делает |
|---|---|
| `ollama` | Сервер модели. Порт только на `127.0.0.1`, наружу не смотрит |
| `ollama-pull` | Одноразовое скачивание весов и выход |

`ollama-pull` — тот же образ с другой командой, ровно как `migrate` рядом с `api`.
Том ему не нужен: качает сервер по `OLLAMA_HOST`, а не этот CLI.

Веса лежат в томе `ollama` и переживают деплой по тому же механизму, что `pgdata` и
`uploads`: `cd.yml` гасит стек через `docker compose down` **без `-v`**. Качать 400 МБ
на каждый деплой не приходится, а `make reset` сносит их вместе с базой.

**Диск.** Образ `ollama/ollama` — 6.3 ГБ: внутри лежат библиотеки CUDA и ROCm, которые
на сервере без GPU не используются вовсе. Плюс 0.4 ГБ весов. На 25 ГБ сервера это
четверть диска — влезает, но заметно. Понадобится место — образ `llama.cpp` server в
разы компактнее, ценой ручной сборки и своего формата запуска.

**У `api` нет `depends_on` на Ollama.** Сайт обязан подниматься, пока модель качается.

Имя модели подставляется с дефолтом (`${OLLAMA_MODEL:-qwen2.5:0.5b}`), поэтому деплой
не требует правки `.env` на сервере — но переменной там можно переопределить.

## Ограничения текущей версии

- **Антискама в чате обмена нет.** Вторая задача под ту же модель и тот же приём:
  классификация с ответом по схеме, жалоба в существующую очередь модерации.
- **Автоответчик отвечает один раз и только на первое сообщение обращения.** Второй
  вопрос в том же треде ждёт человека.
- **Задачи не переживают рестарт.** Очередь в памяти: упал процесс между созданием
  обращения и ответом — автоответа не будет. Обращение при этом на месте, и оно в
  очереди модерации.
- **Ответ не кешируется.** Одинаковый вопрос считается заново. До появления нагрузки
  измерять нечего.
- **Тег модели не менялся, хотя замер советует.** `qwen2.5:0.5b-instruct-q8_0` на одном
  потоке точнее на один кейс из пятнадцати и при этом на 13% быстрее q4_K_M: на 0.5B
  распаковка q4 дороже, чем экономия на объёме. Цена — +127 МиБ памяти. Переключается
  одной строкой в `internal/config` и подстановкой в compose.
- **Модель одна на весь сервис.** Понадобится вторая — понадобится и вторая машина.
- **Скачивание не проверяет целостность сверх того, что делает сам Ollama**, и при
  обрыве связи `ollama-pull` завершится ошибкой; лечится повторным `make llm`.
- **Веса выгружаются из памяти через 30 секунд простоя** (`OLLAMA_KEEP_ALIVE` в
  прод-оверлее) и возвращают память базе. Плата — перезагрузка с диска на следующем
  обращении; в фоновой задаче это незаметно.

## Запуск и проверка

```bash
make llm                                # поднять Ollama и скачать веса
docker compose logs ollama-pull         # чем кончилось скачивание
curl -s localhost:11434/api/tags        # модель в списке

go test ./internal/llm/...              # ни сети, ни Ollama: httptest
go test ./internal/support/service/...  # логика автоответчика на поддельной модели
make test-support-bot-llm               # точность роутера на живой модели, порог 9 из 15
```

Автоответчик руками: зарегистрироваться, открыть «Поддержка», создать обращение — ответ
появляется в треде через несколько секунд (страница опрашивает тред каждые 3 с) и
приносит уведомление. В логе API на каждое обращение либо ничего, либо строка
`support bot ...` с причиной, по которой ответа не будет.

Поведение пинга на старте — три исхода:

```bash
make run                                     # llm: model ... is ready
OLLAMA_URL= make run                         # llm: OLLAMA_URL is empty ...
docker compose stop ollama && make run       # llm: model ... is not ready at startup
```

Во всех трёх случаях API поднимается и отвечает на `/health`.
