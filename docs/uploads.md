# Загрузка фотографий

Фотография вещи и аватарка раньше были внешними ссылками: человек должен был сам выложить
снимок куда-то ещё и принести адрес. Для сервиса обмена это неработающий сценарий —
вещь фотографируют телефоном, а не публикуют ради ссылки.

Модуль принимает файл, кладёт его на диск и возвращает путь. В БД по-прежнему лежит строка,
и колонки не изменились: `items.photo_urls text[]`, `users.photo_url text`. Миграции у этой
фичи нет вовсе.

## Загрузка отделена от объявления

```
POST /uploads  (multipart)  →  {"url": "/uploads/<uuid>.jpg"}
POST /items    {"photo_urls": ["/uploads/<uuid>.jpg", ...]}
```

Файл и объявление — два разных запроса. Альтернатива, multipart прямо в `POST /items`,
переписала бы весь путь создания и изменения вещи: там частичное обновление, разница между
«поле не передали» и «передали пустым», транзакция на две таблицы. Ничего из этого трогать
не пришлось.

Побочный эффект того же решения: аватарке этот эндпоинт достался бесплатно — она хранит
такую же строку, и `PATCH /users/{id}` про загрузку ничего не знает.

Сама по себе загрузка ни к чему файл не привязывает. Загрузил и передумал — на диске
остался файл, на который никто не ссылается.

## API

| Метод и путь | Кому | Что делает |
|---|---|---|
| `POST /uploads` | авторизованному | Принимает один файл, возвращает ссылку на него |
| `GET /uploads/{файл}` | любому, без авторизации | Отдаёт файл |

Запрос — `multipart/form-data` с полем `file`:

```bash
curl -b cookies.txt -X POST http://localhost:8080/uploads -F "file=@bike.jpg"
```

Ответ `201`:

```json
{ "url": "/uploads/8db9f3e2-8a45-4a70-b3d1-167b4f97e121.jpg" }
```

| Код | Когда возвращается |
|---|---|
| `201 Created` | Файл сохранён |
| `400 Bad Request` | В запросе нет поля `file` или это не картинка поддерживаемого формата |
| `401 Unauthorized` | Нет или истекла cookie `access_token` |
| `413 Payload Too Large` | Файл больше 5 МБ |

Отдача публична намеренно: карточка вещи и профиль видны без входа, значит видны и их
фотографии. Прятать файл за авторизацией, когда ссылка на него лежит в публичном JSON,
смысла нет.

## Что проверяется на входе

- **Тип — по содержимому, а не по имени.** `http.DetectContentType` смотрит первые 512 байт,
  принимаются `image/jpeg`, `image/png`, `image/webp`. Имя файла из браузера не участвует
  вообще: под `.jpg` приезжает что угодно, а расширение выдаёт сервер по результату снифа.
- **Имя генерирует сервер** — `uuid` + расширение. Клиентское имя не попадает ни в путь, ни в
  ответ, поэтому склеить путь из чужой строки невозможно в принципе.
- **Размер — 5 МБ**, и ограничение стоит дважды: `http.MaxBytesReader` на теле запроса
  (плюс 32 КБ на границы multipart) и `io.LimitReader` на самой картинке. Недописанный файл
  при отказе удаляется.
- **Каталог не листается.** `GET /uploads/` отдаёт `404`: листинг раскрыл бы ссылки на все
  фотографии сервиса разом.

Заголовки отдачи: `Cache-Control: public, max-age=31536000, immutable` (имя содержит uuid,
содержимое по ссылке не меняется никогда) и `X-Content-Type-Options: nosniff`.

## Что считается ссылкой на фотографию

Одно правило на оба поля, живёт в `uploadservice.IsPath` и в валидации сервисов вещей и
пользователей:

| Значение | Принимается | Почему |
|---|---|---|
| `/uploads/<файл>.jpg` | да | наш файл |
| `https://example.com/1.jpg` | да | внешние ссылки остались валидными |
| `/uploads/../../etc/passwd` | нет | после префикса допустимо ровно одно имя файла |
| `//evil.com/1.jpg` | нет | протокол-относительный адрес уводит браузер на чужой домен |
| `photo.jpg` | нет | относительный путь останется битой картинкой |

Внешние ссылки принимаются не из вежливости: с ними лежат объявления и профили, созданные до
этой фичи. Запрет сломал бы им **редактирование** — списки заменяются целиком, и старые
ссылки приезжают обратно вместе с новой фотографией.

Заодно закрылась дыра в профиле: `users.photo_url` не проверялся никак, в него уезжала любая
строка.

## Где лежат файлы

Каталог задаёт `UPLOADS_DIR`, по умолчанию `./uploads` рядом с процессом. В `docker-compose`
это том `uploads`, примонтированный только в `api`.

Том переживает деплой по тому же механизму, что и `pgdata`: `cd.yml` гасит стек через
`docker compose down` **без `-v`**. Отсюда два следствия для эксплуатации:

- **том нужно бэкапить** рядом с базой. Имена файлов — uuid, содержимое не перезаписывается
  никогда, поэтому инкрементальный `rsync` здесь тривиально корректен;
- `make reset` и `docker compose down -v` сносят фотографии вместе с базой — это одна и та же
  команда и одно и то же «начать с нуля».

В `Dockerfile` каталог создаётся с владельцем `nobody` до `USER nobody`. Пустой том Docker
наследует владельца точки монтирования из образа; без этой строки том создался бы `root:root`
и api не смог бы записать в него ни одной фотографии — причём только на чистой машине, где
тома ещё нет.

Раздаёт файлы сам Go, а не Caddy: `handle /uploads/*` в `Caddyfile` проксирует их туда же,
куда и API, а в разработке то же делает прокси Vite. Один путь на обе среды — раздача
статики Caddy напрямую из тома была бы быстрее, но потребовала бы второй, не проверяемый
локально маршрут.

## Клиент

Загрузчик один на оба сценария — `PhotoUploader`. Разница выражена через `max`: у вещи это
10 фотографий, порядок и пометка «Обложка» на первой (её видит вторая сторона в списке), у
аватарки `max={1}` и новый файл заменяет старый.

Перед отправкой фотография уменьшается в браузере: `createImageBitmap` → `canvas` →
`toBlob("image/webp", 0.85)`, если большая сторона больше 1600 px. Телефон отдаёт оригинал на
8 мегапикселей, а показывается фотография максимум в несколько сотен. Любая осечка —
старый браузер, битый файл — отправляет оригинал: доставить фотографию важнее, чем сжать её.

Файлы уходят по одному и последовательно. Параллельные загрузки дописывали бы ссылку каждая
к своему снимку списка, и до формы доехала бы только последняя.

## Ограничения текущей версии

- **Мусор не убирается.** Заброшенные при заполнении формы файлы, фотографии удалённых
  объявлений и заменённые аватарки остаются на диске. После уменьшения на клиенте это
  200–400 КБ за штуку: 1000 объявлений по 10 фотографий — около 3 ГБ. Когда начнёт мешать,
  лечится командой, которая удаляет файлы старше суток, отсутствующие в `items.photo_urls` и
  `users.photo_url`.
- Ограничения по частоте загрузок нет — только авторизация и лимит размера.
- Превью не создаются: в списке показывается тот же файл, что и в галерее.
- Файлы лежат на диске приложения. Второй сервер или CDN потребуют объектного хранилища;
  тогда изменится только `uploadservice`, потому что в БД лежит строка, а не файл.

## Запуск и проверка

```bash
make db     # PostgreSQL с миграциями
make run    # API на localhost:8080

go test ./internal/upload/...   # БД не нужна: t.TempDir() и httptest
```

Живьём, через поднятый `make up`:

```bash
curl -b cookies.txt -X POST http://localhost/api/uploads -F "file=@bike.jpg"
curl -o copy.jpg http://localhost/uploads/<файл>   # отдаётся без авторизации
curl -o /dev/null -w "%{http_code}\n" http://localhost/uploads/   # 404, листинга нет
```
