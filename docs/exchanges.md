# API обменов

Этот модуль позволяет авторизованному пользователю посмотреть обмены, которые нашла
система. Во внешнем API используется только слово «обмен». Внутреннее устройство графа
и названия таблиц клиенту знать не нужно.

Внутренний алгоритм подробно описан в [документе о поиске обменов](exchange-search.md).

## Жизненный путь обмена

| Статус | Что означает | Чем двигается дальше |
|---|---|---|
| `proposed` | подбор нашёл состав, участники решают | согласием всех участников |
| `confirmed` | все согласились, объявления зарезервированы | сдачей всех вещей в пункты выдачи |
| `delivering` | все вещи лежат в пунктах | администратором, когда пункты выдали вещи |
| `delivered` | пункты передали вещи получателям | подтверждением получения всеми участниками |
| `completed` | обмен состоялся | — |
| `cancelled` | обмен закрыт отказом участника, чужим подтверждением или администратором | — |

У отменённого обмена поле `cancel_reason` уточняет причину: `proposal_declined`,
`confirmed_broken`, `superseded`, `item_withdrawn`, `user_blocked`, `admin_cancelled` или
`legacy` для старых данных. У остальных статусов оно равно `null`.

Переход `confirmed → delivering` backend делает сам: в тот момент, когда в пунктах
оказывается последняя вещь обмена. Вещь можно отнести и заранее — тогда цепочка уходит в
доставку сразу после того, как согласится последний участник. Как отмечать вещь, описано в
[документе о пунктах выдачи](pickup-points.md).

Переход `delivering → delivered` делает административная панель: backend на него никого не
переводит сам, потому что факт выдачи вещи он проверить не может.

Отказаться от участия можно только на `proposed` и `confirmed`. Дальше вещи уже уехали в
пункты, и закрыть обмен может только администратор.

## Маршруты

### `GET /exchanges`

Возвращает все обмены, в которых участвует текущий пользователь. Авторизация берётся из
cookie `access_token`.

Если обменов пока нет, сервер отвечает кодом `200` и пустым JSON-массивом:

```json
[]
```

### `GET /exchanges/{id}`

Возвращает один обмен по UUID. Посмотреть его может только участник этого обмена.

- `400` — в адресе передан не UUID;
- `401` — пользователь не авторизован;
- `403` — обмен существует, но текущий пользователь в нём не участвует;
- `404` — обмен с таким ID не существует;
- `500` — внутренняя ошибка backend.

### `POST /exchanges/{id}/decline`

Отменяет предложенный или уже подтверждённый обмен. При отмене подтверждённого обмена
зарезервированные объявления снова становятся доступными. В обоих случаях backend затем
запускает поиск новых обменов. Отказ от ещё не подтверждённого предложения читается как «не
хочу эту вещь»: подбор больше не предложит её отказавшемуся ни в одном составе. Подробный
сценарий описан в [документе о восстановлении](exchange-recovery.md).

Отказ доступен, пока обмен в статусе `proposed` или `confirmed`. На `delivering` и
`delivered` backend отвечает `409`.

### `POST /exchanges/{id}/complete`

«Товар получен»: участник подтверждает, что забрал свою вещь. Доступен только на статусе
`delivered` — до выдачи подтверждать нечего, и backend отвечает `409`. Когда получение
подтвердят все участники, обмен переходит в `completed`, объявления помечаются переданными,
их отметка о пункте снимается, а `deals_completed` участников увеличивается.

Завершение открывает оценку партнёра: 14 дней участник может поставить балл тому, от кого
получил вещь. Состояние оценки приезжает прямо в ответе обмена — поле `rating`, см.
[оценку партнёра](ratings.md).

## Формат ответа

```json
{
  "id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
  "status": "confirmed",
  "cancel_reason": null,
  "participants": [
    {
      "user": {
        "id": "11111111-1111-1111-1111-111111111111",
        "nickname": "samir",
        "photo_url": null
      },
      "gives_item": {
        "id": "bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb",
        "title": "Настольная игра",
        "description": "Полный комплект",
        "status": "reserved",
        "category": {
          "slug": "hobby",
          "name": "Хобби"
        },
        "pickup_point": {
          "id": "dddddddd-dddd-dddd-dddd-dddddddddddd",
          "name": "ПВЗ на Ленина",
          "address": "Казань, улица Ленина, 10"
        }
      },
      "receives_item": {
        "id": "cccccccc-cccc-cccc-cccc-cccccccccccc",
        "title": "Книга",
        "description": "В хорошем состоянии",
        "status": "reserved",
        "category": {
          "slug": "books",
          "name": "Книги"
        },
        "pickup_point": null
      },
      "position": 0,
      "status": "accepted",
      "decided_at": "2026-08-05T12:30:00Z"
    }
  ],
  "unread_count": 2,
  "rating": null,
  "created_at": "2026-08-05T12:00:00Z",
  "updated_at": "2026-08-05T12:00:00Z",
  "closed_at": null
}
```

`position` задаёт порядок участников. У каждого участника отдельно указаны объявление,
которое он отдаёт (`gives_item`), и объявление, которое он получает (`receives_item`).

`pickup_point` у вещи — пункт, в котором она лежит, или `null`, если она ещё дома. По нему
видно, кого из участников ждут, чтобы обмен ушёл в доставку.

`rating` — кого текущему пользователю оценивать, до какого момента и что он уже поставил.
`null` на любом статусе кроме `completed` и у постороннего. Кого оценивать, считает сервер:
повторять это правило на клиенте значило бы завести второй источник правды.

`unread_count` — сколько сообщений и событий в треде обмена появилось с тех пор, как текущий
пользователь читал его в последний раз. Сам тред живёт отдельным маршрутом, см.
[документ о переписке](exchange-messages.md).

## Разделение ответственности

- handler занимается маршрутом, авторизацией, UUID и HTTP-кодами;
- service проверяет, что пользователь участвует в запрошенном обмене;
- repository только читает данные из PostgreSQL;
- DTO формирует безопасный JSON для frontend.
