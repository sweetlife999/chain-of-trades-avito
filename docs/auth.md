# Аутентификация и авторизация

Этот модуль позволяет пользователю войти в систему, оставаться авторизованным между
запросами и обращаться к защищённым маршрутам.

Два похожих термина означают разные вещи:

- **аутентификация** отвечает на вопрос «кто делает запрос?»;
- **авторизация** отвечает на вопрос «разрешено ли этому пользователю действие?».

Например, JWT подтверждает, что запрос отправил определённый пользователь — это
аутентификация. Сравнение его ID с ID профиля перед обновлением — авторизация.

## Как работает вход

```text
nickname + password
        ↓
поиск пользователя в PostgreSQL
        ↓
сравнение пароля с bcrypt-хешем
        ↓
создание подписанного JWT на 12 часов
        ↓
JWT сохраняется в HttpOnly cookie
```

JWT содержит ID пользователя и время окончания действия. Он подписан секретом backend,
поэтому изменить ID или срок действия незаметно не получится. JWT не шифруется, поэтому
в него нельзя класть пароль или другие секретные данные.

## Маршруты

| Метод и путь | Что делает | Успешный ответ |
|---|---|---|
| `POST /auth/login` | Проверяет nickname и password, создаёт cookie | `200 OK` |
| `POST /auth/logout` | Удаляет cookie | `204 No Content` |
| `GET /auth/me` | Возвращает текущего пользователя | `200 OK` |

Регистрация остаётся в модуле пользователей: `POST /users`.

### Вход

```http
POST /auth/login
Content-Type: application/json
```

```json
{
  "nickname": "Samir",
  "password": "password123"
}
```

Nickname ищется без учёта регистра, поэтому `Samir` и `samir` относятся к одному
пользователю. Пароль сравнивается с bcrypt-хешем из БД. Открытый пароль и
`password_hash` не возвращаются клиенту.

При успешном входе backend возвращает безопасные данные пользователя и добавляет
заголовок `Set-Cookie`:

```text
access_token=<JWT>; Path=/; Max-Age=43200; HttpOnly; SameSite=Lax
```

JWT не передаётся в JSON. Браузер сохраняет cookie и затем автоматически прикладывает её
к запросам на тот же сайт.

При неизвестном nickname и неправильном пароле возвращается одинаковая ошибка. По ней
нельзя определить, зарегистрирован ли конкретный nickname:

```json
{
  "error": "invalid nickname or password"
}
```

### Текущий пользователь

```http
GET /auth/me
Cookie: access_token=<JWT>
```

Middleware проверяет cookie до вызова handler:

1. Cookie существует и не пустая.
2. Токен подписан ожидаемым секретом.
3. Используется только алгоритм `HS256`.
4. Присутствует срок действия `exp`, и он ещё не истёк.
5. Поле `sub` содержит корректный UUID пользователя.

После проверки ID пользователя записывается в `context` текущего HTTP-запроса. Handler
`GET /auth/me` получает этот ID из context, загружает пользователя из БД и возвращает
его без `password_hash`.

### Выход

```http
POST /auth/logout
```

Backend отправляет cookie с пустым значением и прошедшим сроком действия. Браузер
удаляет её. Сам JWT нельзя отозвать на сервере раньше срока, но после удаления cookie
браузер перестаёт его отправлять.

## Защита профиля

Маршрут `PATCH /users/{id}` требует аутентификацию. После проверки JWT ID текущего
пользователя сравнивается с `{id}` в адресе:

- ID совпадают — профиль можно изменить;
- cookie отсутствует или токен некорректен — `401 Unauthorized`;
- пользователь пытается изменить другой профиль — `403 Forbidden`.

Получение профиля через `GET /users/{id}` и регистрация через `POST /users` остаются
публичными для MVP.

## Что хранится в JWT

Используются стандартные claims:

| Claim | Значение |
|---|---|
| `iss` | Имя сервиса `chain-of-trades-avito` |
| `sub` | UUID пользователя |
| `iat` | Время создания токена |
| `exp` | Время окончания действия через 12 часов |

Подпись создаётся алгоритмом `HS256`. При чтении токена backend явно разрешает только
этот алгоритм, а также проверяет подпись, issuer и expiration.

## Cookie

| Параметр | Зачем нужен |
|---|---|
| `HttpOnly` | JavaScript в браузере не может прочитать JWT |
| `SameSite=Lax` | Снижает риск отправки cookie в нежелательных межсайтовых запросах |
| `Path=/` | Cookie работает для всех маршрутов API |
| `Max-Age=43200` | Cookie живёт 12 часов, как и JWT |
| `Secure` | В production разрешает отправку cookie только через HTTPS |

Для локальной разработки используется обычный HTTP, поэтому `COOKIE_SECURE=false`. В
production эта переменная должна быть равна `true`.

## Коды ответа

| Код | Когда возвращается |
|---|---|
| `200 OK` | Вход выполнен или текущий пользователь получен |
| `204 No Content` | Выход выполнен, тела ответа нет |
| `400 Bad Request` | Некорректный JSON входа |
| `401 Unauthorized` | Неверные данные входа, cookie отсутствует или JWT не прошёл проверку |
| `403 Forbidden` | Пользователь пытается изменить чужой профиль |
| `500 Internal Server Error` | Непредвиденная ошибка backend |

## Где находится код

```text
internal/auth/
├── authcontext/  — сохраняет и читает ID пользователя из context
├── dto/          — JSON запроса на вход и ошибки
├── handler/      — маршруты login, logout и me
├── middleware/   — проверяет cookie и JWT
├── service/      — проверяет пароль и создаёт токен
└── token/        — подписывает и разбирает JWT
```

Модуль использует существующий `internal/user/repository`: по nickname он получает
пользователя с хешем для проверки пароля, а по ID — данные для `/auth/me`.

## Настройка

В `.env` нужны две переменные:

```dotenv
JWT_SECRET=<случайная строка длиной не меньше 32 символов>
COOKIE_SECURE=false
```

Настоящий `JWT_SECRET` хранится только в `.env`, который игнорируется Git. В репозитории
есть лишь пример `.env.example`.

## Запуск и ручная проверка

```bash
make up
make run
```

Сначала зарегистрировать пользователя:

```bash
curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Samir","password":"password123"}'
```

Войти и сохранить cookie во временный файл:

```bash
curl -i -c /tmp/auth.cookies -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Samir","password":"password123"}'
```

Получить текущего пользователя:

```bash
curl -i -b /tmp/auth.cookies http://localhost:8080/auth/me
```

Выйти:

```bash
curl -i -b /tmp/auth.cookies -X POST http://localhost:8080/auth/logout
```

Автоматические проверки запускаются командой:

```bash
go test ./...
```

Тесты отдельно проверяют правильный и неправильный пароль, подпись, алгоритм и срок
действия JWT, middleware, параметры cookie, маршруты и коды `401`/`403`.

## Ограничения MVP

- refresh-токенов нет — через 12 часов нужно войти снова;
- ролей и прав администратора нет;
- восстановления пароля нет;
- входа через сторонние сервисы нет;
- серверного списка отозванных JWT нет.

Для текущего MVP этого достаточно: пользователь может зарегистрироваться, войти,
получить свой профиль, безопасно изменить его и выйти.
